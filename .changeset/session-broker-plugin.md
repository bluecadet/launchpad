Add `session()`, the Station session broker plugin. It owns a Node's link to the visitor-identity vendor and holds the one Session its Station currently has, so exhibit apps read a Session over the controller's existing command and SSE surface instead of each re-implementing vendor auth, retry, Profile caching, and degraded-mode fallback. `session({ vendor, idleTimeoutMs, fallbackLanguage })` is the whole configuration surface — endpoints, vendor credentials, retry policy, and polling cadence stay in the adapter and never reach launchpad config or state.

Sessions are last-tap-wins. A different Credential ends the current Session with reason `replaced` and starts a new one; the same Credential refreshes in place, keeping its `sessionId` so an app keyed off it does not flicker when a visitor taps twice. Quiet for `idleTimeoutMs` ends it with `timeout`, and `session.end` with `explicit`. Taps are never serialized, and ordering follows when a tap arrived rather than when its lookup finished, so a slow answer for a Credential that has since been replaced cannot resurrect it. A `fetchProfile` failure still opens the Session, marked `degraded`, on the last Profile cached for that Visitor or else on `fallbackLanguage`; a `resolveCredential` failure drops the tap, because resolving the Credential is exactly what the Profile cache is keyed by.

`session.current` is the authoritative query, `session.end` clears the Station, and `session.tap.simulate` feeds a Credential through the real tap path — which is what makes a full tap-to-render flow demoable against `fakeVendor()` with no wristband and no reader. It is always registered and lets anyone who can reach the transport impersonate a wristband, so leave it out of the transport's `allowedCommands` in production. Four events are declaration-merged onto `LaunchpadEvents`: `session:started`, `session:ended`, `session:current`, and `session:degraded`. Add `session:current` to the transport's `replayEvents` — a transport option a plugin cannot set on your behalf, whose default list omits it — so an app that connects mid-Session rehydrates instead of waiting for the next tap.

Only the five-field thin canon reaches state, the status section, or an event payload; the vendor Profile is an in-memory passthrough served exclusively by `session.current`. Event payloads and command results share one serializer, and events fan out to every authenticated SSE client, so a Profile on `session:started` would be a broadcast. One caveat worth wiring around: `command:success` carries a command's result verbatim, so keep `command:*` out of the transport's `events` filter and out of `observability`'s `include` patterns on any Node running this plugin.

Sessions do not survive a daemon restart, by design rather than by omission: nothing in `VendorClient` asks a vendor who is standing at a Station, so there is nothing to rehydrate from. A restarted daemon comes up idle, the app keeps rendering its last-received copy, and the visitor re-taps into a new `sessionId`. An app crash is the recoverable case — the daemon still holds the Session, so the app rehydrates the moment it reconnects. Commissioning teams should know the restart behavior is intended, not a defect.
