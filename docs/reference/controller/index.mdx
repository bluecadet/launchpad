The controller package coordinates every other subsystem. It owns the plugin lifecycle, routes commands, and hosts the event bus that content, monitor, scheduler, and observability use to communicate.

## Integration with subsystems

Plugins integrate with the controller through these contracts.

Plugin properties are the capabilities a plugin offers the controller:

```typescript
type InstantiatedPlugin<TCommand> = Partial<
  CommandExecutor<TCommand> &  // Execute commands
  Readyable &                  // Act once every plugin is set up
  Disconnectable               // Clean disconnect
>;
```

Plugin config holds controller-owned metadata and lifecycle hooks:

```typescript
interface PluginConfig<TCommand, TState> {
  name: string;
  manifest?: PluginManifest<TCommand>;
  setup(ctx: PluginContext<TState>): ResultAsync<InstantiatedPlugin<TCommand>, Error>;
  summarize?(state: LaunchpadState): Section | null;
}
```

`PluginContext` is the infrastructure the controller provides to the plugin:

```typescript
interface PluginContext<TState = unknown> {
  eventBus: EventBus;          // Type-safe event bus
  logger: Logger;              // Scoped logger
  logSource?: LoggerSource;    // Controller-owned canonical log source
  abortSignal: AbortSignal;    // Cancelled on controller shutdown
  cwd: string;                 // Working directory
  mode: ControllerMode;        // "task" | "persistent" — which mode the controller is running in
  getStatusSnapshot: () => StatusSnapshot; // Aggregates every plugin's summarize(); use sparingly
  dispatchCommand: (command) => ResultAsync<unknown, Error>;
  updateState: (producer: (draft: TState) => void) => void;
  getGlobalState: () => VersionedLaunchpadState;
  onGlobalStatePatch: (handler) => () => void;
}
```

### Explicit command registration

A plugin that handles commands must declare them in `manifest.commands` and implement `executeCommand()`:

```typescript
interface CommandExecutor<TCommand> {
  executeCommand(command: TCommand): ResultAsync<unknown, Error>;
}

definePlugin({
  name: 'my-plugin',
  manifest: {
    commands: [{ id: 'my-plugin.increment' }],
  },
  setup(ctx: PluginContext<MyState>) {
    ctx.updateState(() => ({ count: 0 }));

    return okAsync({
      executeCommand(command) {
        ctx.updateState(draft => { draft.count++; });
        return okAsync(undefined);
      }
    });
  }
});
```

The controller dispatches only registered commands. It does not infer command ownership from name prefixes.

### Logging

The controller owns the canonical segmented JSONL log, an optional human-readable text view, rotation, retention, and the per-destination checkpoint store. `PluginContext.logSource` exposes the source when available. Its `flush` and `createReader` methods, and each reader's `read`, `ack`, and `close` methods, return `ResultAsync`, so callers handle failures explicitly. See [Controller logging](/reference/controller/logging/) for configuration, file-layout migration, locking, and failure behavior.

### Process ownership

Only one controller may be active per configured project identity, in task or persistent mode. The constructor opens no files and acquires no ownership. The first `registerPlugin()` or `start()` call acquires an operating-system lease at `<resolved pidFile>.lock`, before file logging starts or plugin setup runs. Contention, filesystem errors, and missing native locking surface as errors in that method's `ResultAsync`; the constructor never throws for them.

Overlapping `start()` calls share one startup attempt. If startup fails, the controller aborts its signal, waits for registered plugins to disconnect, and closes logging before releasing ownership. `stop()` does the same cleanup, even if plugins were registered before startup or registration failed. If startup is still pending, `stop()` waits for it before shutting down. The `stop` workflow runs only on a started controller.

The controller releases ownership only after plugin shutdown and physical logging I/O settle. Always call and await `stop()` when disposing of a controller, including after failed registration. The logging-close wait is bounded: on timeout, `stop()` logs a warning and finishes, but pending canonical or checkpoint I/O keeps holding both the project and log-directory leases. Until that I/O settles, a successor's `start()` or `registerPlugin()` returns a contention error. Shutdown neither cancels the I/O nor releases ownership early. A stopped controller can't restart or accept new plugins; create a new controller for the next run. If the process crashes, the operating system releases the leases.

The adjacent PID file only helps clients discover a persistent daemon; the lease decides ownership. Task runs don't write a PID file. The lease file is permanent: don't delete, rename, or replace it. Its presence doesn't mean a controller is active.

The lease closes startup races that a PID existence check can't. Concurrent task commands can't start a second local controller, and a task controller can't overlap a persistent controller with the same resolved `pidFile` identity.

### Host-owned workflows

Hosts declare startup and shutdown steps in config and pass them to the controller:

```typescript
export default defineConfig({
  plugins: [content({}), monitor({})],
  workflows: {
    start: ['content.fetch', 'monitor.connect', 'monitor.start'],
  },
});
```

The controller exposes `setWorkflows()` and `runWorkflow()` so every host runs the same named workflows. `LaunchpadController.stop()` runs the `stop` workflow before disconnecting plugins.

#### Step failure handling

Workflows run every step **best-effort**. When a step fails, the controller records the error, emits `workflow:step:error`, and moves on. After the last step, the workflow reports an aggregated failure (`workflow:error`) if any step failed.

A failed `content.fetch` therefore doesn't stop `monitor.start` from launching apps. Content fetching stages its output before promoting it, so the last published content stays on disk and the monitor runs against it.

`launchpad start` logs an aggregated failure and keeps the controller running, so a failed step never takes down apps that started successfully.

To make a step fatal, wrap it in an object with `stopOnError`. If it fails, the workflow halts and skips the remaining steps:

```typescript
export default defineConfig({
  workflows: {
    // 'publish' is skipped if 'build' fails
    deploy: [{ step: 'build', stopOnError: true }, 'publish'],
  },
});
```

### State management

Plugins own their domain logic; the controller owns the state infrastructure. A plugin calls `ctx.updateState()` to create and change its state slice. The controller creates a scoped store on the first call and handles patch generation, versioning, and broadcasting.

`ctx.getGlobalState()` returns the full aggregated state for all plugins and the system. For cross-plugin communication, use `ctx.eventBus` or `ctx.dispatchCommand` instead of polling global state.

### Status snapshots

A plugin adds to `launchpad status` output by defining `summarize(state)` in its plugin config. The controller calls every registered plugin's `summarize()`, drops `null` results, sorts the sections by `order`, and sends the snapshot over IPC.

```typescript
import type { LaunchpadState, Section } from '@bluecadet/launchpad-utils/types';

definePlugin({
  name: 'my-plugin',
  setup(ctx: PluginContext<MyState>) {
    ctx.updateState(() => ({ ready: false }));
    return okAsync({});
  },
  summarize(state: LaunchpadState): Section | null {
    const pluginState = state.plugins['my-plugin'] as MyState | undefined;
    if (!pluginState) return null;

    return {
      name: 'my-plugin',
      title: 'My Plugin',
      rows: [{ type: 'kv', label: 'Ready', value: pluginState.ready ? 'Yes' : 'No' }],
    };
  },
});
```

### Transports

Transports are plugins that expose the command bus and event bus over a wire protocol: the IPC socket the CLI uses, and the [HTTP/SSE transport](/reference/controller/transports/) for browsers and Unity/.NET clients.

### Readyable

Plugin `setup()` runs sequentially in registration order, so plugins registered later miss anything a plugin emits during its own setup. Plugins whose startup work depends on the rest of the system, such as announcing state on the event bus, implement `ready()` instead.

```typescript
interface Readyable {
  ready(): ResultAsync<void, Error>;
}
```

After registering plugins, the host calls `LaunchpadController.ready()`, and the controller calls `ready()` on each plugin in registration order. If a plugin's `ready()` fails or throws, the controller logs the error; startup continues and other plugins' `ready()` still runs. Repeat calls do nothing. A plugin registered after the ready phase is readied right after its `setup()`, so every plugin sees the hook exactly once.

### Disconnectable

Plugins that manage long-lived resources, such as connections or child processes, implement `disconnect()`. The controller calls it after firing `abortSignal`, so in-flight async work is already cancelled.

```typescript
interface Disconnectable {
  disconnect(reason: DisconnectReason): ResultAsync<void, Error>;
}
```

## Usage modes

### Task mode

A task-mode controller is a temporary instance for one-off operations:

1. Create a controller in task mode
2. Start the controller
3. Register subsystems
4. Run the ready phase (`ready()`)
5. Execute the command(s)
6. Stop the controller

The CLI uses task mode when no persistent controller is running. Task mode takes the same project ownership lease as persistent mode, so overlapping task runs fail instead of changing project resources at the same time.

### Persistent mode

A persistent-mode controller stays running to handle many commands. It:

- Starts with `launchpad start`, optionally detached with `-d`
- Registers plugins, then runs the ready phase (`ready()`) once all are set up. For example, the content plugin's startup announcement reaches the HTTP/SSE transport's replay backlog here.
- Opens an IPC socket
- Holds the project ownership lease and writes PID metadata for discovery
- Handles many CLI commands without reinitializing
- Shuts down gracefully with `launchpad stop`

Later `launchpad` commands (content, monitor, status) detect the running controller and talk to it over IPC instead of creating temporary instances.

#### Benefits

- Later commands run faster because they skip initialization.
- All commands share one controller instance and its state.
- Detached mode (`-d`) runs the controller in the background.
- The IPC protocol provides type-safe command execution and state queries.
- Shutdown escalates from IPC to SIGTERM to SIGKILL.

## Type safety

The controller uses TypeScript declaration merging on `@bluecadet/launchpad-utils/types` to type events without circular dependencies:

```typescript
// The controller declares system events
declare module '@bluecadet/launchpad-utils/types' {
  interface LaunchpadEvents {
    'system:shutdown': { code?: number; signal?: string };
    'content:fetch:start': { timestamp: Date };
    'monitor:app:started': { appName: string; pid: number };
  }
}
```
