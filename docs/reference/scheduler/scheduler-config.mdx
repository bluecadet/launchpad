Pass a record keyed by command id to `scheduler()`. Each key names the command to dispatch.

```typescript
scheduler({
  'content.fetch': '5m',
  'content.clear': { cron: '0 3 * * *' },
});
```

> [!NOTE]
> Each command id can have only one schedule.

For a complete content-refresh setup, see the [live content refresh recipe](/recipes/live-content-refresh/).

## Schedule shorthand

A bare string is either a duration or a cron expression:

- A string with no whitespace is a duration, such as `'500ms'`, `'30s'`, `'5m'`, or `'2h'`.
- A string with whitespace is a cron expression and must contain exactly five whitespace-separated fields.

In the object form, durations can also be millisecond numbers.

## Per-job options

Use an object when a job needs options beyond its schedule:

```typescript
scheduler({
  'content.fetch': {
    interval: '5m',
    jitter: '30s',
    retry: {
      forever: true,
      backoff: { initial: '10s', max: '2m', factor: 2 },
    },
    command: { type: 'content.fetch' },
    runOnStart: false,
    enabled: true,
  },
});
```

The schema reference covers each record value. Input defaults exclude values that transforms or the scheduler fill in at runtime; the sections below describe those. Required markers reflect schema structure only, so read the conditional rules for `interval`, `cron`, and the retry policies. See [configuration reference conventions](/reference/cli/config-loading/#configuration-reference-conventions).

### `interval`

<ConfigReference id="scheduler-options" property="interval" />

Duration between runs. The next run is scheduled when the previous dispatch completes, so interval jobs cannot overlap themselves.

### `cron`

<ConfigReference id="scheduler-options" property="cron" />

A five-field cron expression. Cron schedules stay anchored to wall-clock time. The next occurrence is armed before the current dispatch completes; if the command is still in progress, that occurrence is skipped, not queued.

Exactly one of `interval` and `cron` is required.

### `jitter`

<ConfigReference id="scheduler-options" property="jitter" />

Adds a new random positive delay to every scheduled run and retry so a fleet of kiosks does not fire at once.

The default, `true`, depends on schedule type:

- Interval jobs and retry backoff: up to 10% of the delay being scheduled.
- Cron jobs: up to 60 seconds. A percentage of a multi-hour cron gap would push the run far from its wall-clock time, while a 60-second cap spreads a fleet without moving the occurrence much. A nightly `'0 3 * * *'` job still fires within a minute of 3am.

Set a duration for a fixed maximum jitter on either schedule type, or `false` to disable jitter.

### `retry`

<ConfigReference id="scheduler-options" property="retry" />

Failed dispatches retry before the normal schedule resumes. A successful dispatch resets the failure count and backoff. Choose a policy:

- Forever: omit `retry`, use `{}`, or set `forever: true`. Only this policy accepts `backoff` overrides; it rejects `maxAttempts`.
- Limited: set `forever: false` and supply `maxAttempts`. This policy uses the default backoff curve and rejects `backoff` overrides.

```typescript
scheduler({
  'content.fetch': {
    interval: '5m',
    retry: { forever: true, backoff: { initial: '10s', max: '2m', factor: 2 } },
  },
});
```

To stop after a fixed number of failed attempts instead:

```typescript
scheduler({
  'content.fetch': {
    interval: '5m',
    retry: { forever: false, maxAttempts: 3 },
  },
});
```

A command rejected because it is already running counts as an overlap skip. It does not consume an attempt or start backoff.

#### `forever`

<ConfigReference id="scheduler-options" property="retry.forever" />

Selects the retry policy. Omitted means forever; `false` selects limited retries and requires `maxAttempts`. The field metadata lists all accepted inputs together; the policies above state the conditional requirements.

#### `maxAttempts` (limited policy)

<ConfigReference id="scheduler-options" property="retry.maxAttempts" />

Required when `forever: false`, although the combined input schema does not mark it required. Must be a positive integer. It is rejected with `forever: true` or an omitted `forever`, and it cannot be combined with `backoff`.

#### `backoff` (forever policy)

<ConfigReference id="scheduler-options" property="retry.backoff" />

Available only with the forever policy. Omitted fields use the runtime defaults described in the table, not schema input defaults. `initial` and `max` accept duration shorthand or milliseconds; `factor` must be positive.

```typescript
scheduler({
  'content.fetch': {
    interval: '5m',
    retry: { backoff: { initial: '10s' } },
  },
});
```

### `command`

<ConfigReference id="scheduler-options" property="command" />

Overrides the command dispatched for this job, for commands that need a payload. When omitted, the scheduler dispatches `{ type: <record key> }`.

```typescript
scheduler({
  'content.fetch': {
    interval: '5m',
    command: { type: 'content.fetch', force: true },
  },
});
```

### `runOnStart`

<ConfigReference id="scheduler-options" property="runOnStart" />

Dispatches the job immediately when the scheduler starts. When `false`, the first dispatch waits for the scheduled delay.

### `enabled`

<ConfigReference id="scheduler-options" property="enabled" />

When `false`, the job is never scheduled or dispatched and does not appear in the Scheduler status section. `scheduler.pause`, `scheduler.resume`, and `scheduler.trigger` treat its id as unknown, and a broadcast `scheduler.pause` or `scheduler.resume` (no `job` given) skips it.

## Limitations

Schedules and retry state live in memory only. On restart, each job gets a fresh schedule from the current time, and cron occurrences missed while Launchpad was stopped are skipped.
